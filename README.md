# FastAPI Service

## Overview

Production-ready FastAPI service built on Python 3.12+, `uv` for dependency management, and a modular `src/` layout. The service exposes versioned API v1 health probes, a users CRUD REST API, a thin internal posts chat client, Alembic migrations, and autogenerated OpenAPI documentation.

## Requirements

- Python 3.12+
- [`uv`](https://github.com/astral-sh/uv)
- Docker (optional)

## Quick Start

```bash
uv sync
cp .env.example .env
docker compose up -d postgres
uv run alembic upgrade head
uv run serve
```

The service starts on `http://localhost:8000`.

To exercise the posts chat flow, also configure the upstream dependency in `.env`:

```bash
CHAT_API_BASE_URL=http://localhost:9000
CHAT_API_POSTS_PATH=/chat/posts
CHAT_API_TIMEOUT_SECONDS=10.0
CHAT_API_TOKEN=
CHAT_API_TOKEN_HEADER=Authorization
CHAT_API_FORWARD_HEADERS=authorization,cookie,x-request-id
```

## API Documentation

- Swagger UI: `http://localhost:8000/api/docs`
- ReDoc: `http://localhost:8000/api/redoc`
- OpenAPI JSON: `http://localhost:8000/api/openapi.json`

## Users API

Base path: `/api/v1/users`

- `POST /api/v1/users`
- `GET /api/v1/users?page=1&limit=20`
- `GET /api/v1/users/{user_id}`
- `PATCH /api/v1/users/{user_id}`
- `DELETE /api/v1/users/{user_id}`

The API enforces unique emails, validates UUID path parameters through FastAPI/Pydantic, and returns `404` for missing users plus `409` for duplicate emails.

## Posts Chat

This repository does not contain an existing signed-in product chat surface or auth stack. To keep scope aligned with the Asana task, the implementation adds the thinnest internal client that exercises the dependent posts chat API without introducing a separate frontend app.

Base path: `/api/v1/chat`

- `POST /api/v1/chat/posts`

The request shape is:

```json
{
  "question": "What themes show up in my recent posts?",
  "session_id": "optional-follow-up-session"
}
```

The normalized response shape is:

```json
{
  "answer": "You mostly write about release notes and migrations.",
  "state": "answered",
  "session_id": "returned-session-id",
  "citations": [
    {
      "title": "Release notes recap",
      "url": "https://example.com/posts/1",
      "excerpt": "I wrapped up the migration checklist.",
      "post_id": "1"
    }
  ]
}
```

`state` is always one of:

- `answered`
- `no_posts`
- `insufficient_evidence`

The endpoint forwards configured inbound headers such as `Authorization` and `Cookie` to the upstream dependency so an external gateway or browser session can supply user identity.

## Internal Chat Page

- Internal page: `http://localhost:8000/internal/chat`

The page is intentionally small: a textarea, submit button, message list, citation rendering, distinct empty/fallback states, and client-side `session_id` reuse for follow-up turns.

## Manual Verification

1. Start the app with `CHAT_API_BASE_URL` pointing at the chat dependency.
2. Open `http://localhost:8000/internal/chat`.
3. Submit a question that should return grounded evidence.
   Expect answer text plus at least one visible citation under the assistant response.
4. Submit a question as a user with no posts.
   Expect a `No posts yet` response state, distinct from the initial empty page state.
5. Submit a question that cannot be answered from existing posts.
   Expect a `Not enough information` response state, distinct from the no-posts state.
6. Submit a follow-up turn after a successful answer.
   Expect the page status line to mention the latest `session_id`, and confirm the follow-up request sends that `session_id` back to `/api/v1/chat/posts`.

## Health Check Endpoints

### Liveness

```bash
curl http://localhost:8000/api/v1/health/live
```

Example response:

```json
{
  "status": "ok",
  "timestamp": "2026-05-26T12:00:00Z"
}
```

```bash
curl http://localhost:8000/api/v1/health/ready
```

{
